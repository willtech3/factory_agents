Open questions

  • Is a due date a calendar date (e.g. 2026-11-30) or a date-and-time (e.g. 2026-11-30T17:00:00Z)? non-blocking
    Default if unanswered: A calendar date in ISO-8601 form (YYYY-MM-DD). It matches 'due date' in the outcome and avoids timezone input from clients. Datetimes are rejected with 422.
  • When does a todo become overdue: on its due date, or only once the due date has fully passed? And against which timezone? non-blocking
    Default if unanswered: Overdue when the due date is strictly before today's date in UTC. A todo due today is not overdue until the UTC day ends. UTC matches how created_at is already recorded.
  • Should a completed todo whose due date has passed be flagged overdue? non-blocking
    Default if unanswered: No. `overdue` is false for any done todo, so the flag agrees with GET /todos/overdue, which the outcome defines as open todos only.
  • May a client create a todo with a due date already in the past? non-blocking
    Default if unanswered: Yes. It is accepted and immediately shows as overdue. This lets people log tasks that are already late, and it keeps tests simple.
  • Are the new response keys acceptable as `due_date` (null when unset) and `overdue`, and should a todo without a due date include `due_date: null` rather than omit the key? non-blocking
    Default if unanswered: Yes to both. Every todo always has both keys, so clients see one stable shape. Existing keys are untouched.
  • Does the platform need anything beyond the existing service_manifest.json and preview.yml to deploy this change? (The platform-contract skill was not available in this session to confirm.) non-blocking
    Default if unanswered: No. The change adds no env vars, ports, migrations or infrastructure, so the current manifest (sample-todo, /health, migrations `true`) and preview workflow are used unchanged.

Explicitly out of scope

  • Changing or clearing a due date after creation. The API has no update (PATCH/PUT) endpoint today, and adding one is a new capability the outcome does not ask for. If owners want it, it is a follow-up item.
  • Un-completing a todo. No such operation exists today, and the outcome does not need one.
  • Reminders, notifications, or any push mechanism telling people a task is late. The outcome asks for visibility in API responses only.
  • Filtering or sorting GET /todos by due date, and pagination. The outcome asks only for the overdue view and the flag.
  • Per-user timezones. There are no users or accounts in the service, so 'past due' is judged against one server-side reference time (see open questions).
  • Persistence. Storage stays in memory, as the outcome's constraints require, so due dates are lost on restart just like todos are today.
  • A CI workflow that runs the tests. None exists today, and preview.yml only deploys. Adding one would touch .github/, which is outside the outcome's paths in scope.
  • Response models or OpenAPI schema clean-up beyond what the new field needs. Today's routes return plain dicts, and this item does not refactor them.

Assumptions and risks

  • Adding new keys (`due_date`, `overdue`) to todo responses is not a 'change to the shape of existing fields'. Existing fields keep their names, types and values. Research confirmed no existing test compares a whole todo dict or its exact key set.
  • Clients that send unknown fields are unaffected. TodoIn does not forbid extra keys today, and this item does not change that.
  • 'Any listing' covers GET /todos and GET /todos/overdue. For consistency, the single todo returned by POST /todos and POST /todos/{id}/complete carries the same keys.
  • The overdue list uses the same ordering as GET /todos (ascending id) and returns 200 with [] when nothing is overdue.
  • The work stays inside the outcome's paths in scope: app/**, tests/** and README.md. service_manifest.json and .github/ are not touched.
  • The platform-contract skill could not be found in this session. Deployability was judged from the repo's service_manifest.json and .github/workflows/preview.yml. The workflow deploys any push to factory/** branches without needing app changes.
  • The test suite could not be run during research because the sandbox has no dependencies installed. The pass/fail state of the existing tests is inferred from reading them, not observed.
  • Tests that depend on the current date become flaky, for example a due date of 'today' or 'yesterday' computed in the test run around midnight UTC.
  • The overdue flag is computed once at creation and stored, so it goes stale as time passes.
  • A future GET /todos/{todo_id} route registered before /todos/overdue would shadow it and return 422.
  • The owner wants date-and-time due dates or local-time semantics instead of the proposed UTC calendar date. The rule then has to be revisited after specification.

Approach

This is one coherent change to a small FastAPI service (about 100 lines of app code), so it is one work item and one pull request.

The change has three parts:

  • Optional due date. A todo can take an optional due date when it is created.
  • Overdue flag. Every todo the API returns carries a computed overdue flag.
  • Overdue view. A new GET /todos/overdue returns the open todos whose due date has passed.

Clients that send only a title keep getting exactly the fields and values they get today. The only difference is two added keys: due_date: null and overdue: false.

Why not split it? I considered two items: field and flag first, endpoint second. I decided against it because:

  • Both halves depend on one rule for what "overdue" means.
  • A reviewer should approve that rule once, together with the tests that pin it down.
  • Each half would be XS, and the split would only add a merge dependency.

The tests and the README note go inside the item, not into separate items.

Owner decision. The item is flagged human_judgement_required because what counts as "past due" is a product decision:

  • whether the due date is a date or a date-and-time,
  • which timezone applies,
  • whether a task is overdue on its due day or only after it.

Proposed defaults are below. If you accept them, the item can go straight to specification.

Platform. The change needs none of the following:

  • a database,
  • a new dependency,
  • a new environment variable,
  • any change to service_manifest.json.

The existing .github/workflows/preview.yml deploys it as it is.
