# Optional due date on todos, overdue flag, and GET /todos/overdue

`spec_wi-due-dates-overdue` · item `wi-due-dates-overdue` · outcome `out_4e93d2a0d0` · rev 1 · size S

## Goal
After this merges, a client can send an optional calendar due_date (YYYY-MM-DD) when creating a todo; every todo the API returns carries due_date (null when unset) and a boolean overdue computed at response time; and GET /todos/overdue returns exactly the overdue todos in ascending id order. A todo is overdue if and only if it is open and its due_date is strictly before the current UTC calendar date. This moves the outcome's two metrics: 'Overdue visibility' (GET /todos/overdue returns exactly the open past-due todos and every listed todo carries the flag, measured by the new API tests) and 'Backwards compatibility' (title-only clients and the three existing tests are unchanged, and a todo without a due date is never overdue). The goal is missed if, on the running service, any todo's overdue flag disagrees with the rule, GET /todos/overdue differs from the flagged todos, a title-only POST changes any existing field, or a malformed due_date is stored instead of returning 422; the preview e2e checks and the pytest suite are written to catch each of these.

## Non-goals
- Changing or clearing a due date after creation (no PATCH/PUT), or un-completing a todo.
- Reminders or notifications; filtering, sorting or paginating GET /todos by due date.
- Datetime due dates, per-user timezones, or any timezone other than UTC.
- Persistence or a database; storage stays an in-memory dict.
- Response models or OpenAPI clean-up; routes keep returning plain dicts.
- Any CI workflow, service_manifest.json, pyproject.toml, or .github/ change.
- Adding a GET /todos/{todo_id} route.

## Interfaces
- **Todo response object** (http_api, modified): Every todo returned by any endpoint is this JSON object. Existing keys keep name, type and value; two keys are appended. {"id": 1, "title": "Write the outcome", "done": false, "created_at": "2026-10-10T08:10:54.068302+00:00", "due_date": "2026-11-30", "overdue": false} id:int, title:str, done:bool, created_at:str (ISO-8601, unchanged), due_date: str|null ("YYYY-MM-DD", null when unset), overdue: bool (true iff done is false AND due_date is not null AND date.fromisoformat(due_date) < today_utc()). Both new keys are always present.
- **POST /todos** (http_api, modified): Request body: {"title": str (1..200 chars, unchanged), "due_date": str|null (optional, default null)}. due_date must match ^[0-9]{4}-[0-9]{2}-[0-9]{2}$ and be a real calendar date, otherwise 422. Unknown extra fields are still ignored as today. Response: 201 with the Todo response object. Example: {"title":"Pay rent","due_date":"2026-11-30"} -> 201 {"id": 1, "title": "Pay rent", "done": false, "created_at": "2026-10-10T08:10:54.068302+00:00", "due_date": "2026-11-30", "overdue": false}
- **GET /todos** (http_api, modified): No parameters. 200 with list[Todo response object] ordered by ascending id; [] when empty. Only change: each element carries due_date and overdue.
- **GET /todos/overdue** (http_api, new): No parameters. 200 with list[Todo response object] holding exactly the todos where overdue is true, ordered by ascending id; [] when none. Evaluated against one today_utc() reading per request. It is a GET route on a literal path; no GET /todos/{todo_id} route exists, and if one is ever added it must be registered after this route.
- **POST /todos/{todo_id}/complete** (http_api, modified): Unchanged request and 404 behaviour. The 200 response is the Todo response object, so it carries due_date and overdue (overdue is false because done is true).
- **app.storage.today_utc** (function, new): def today_utc() -> datetime.date: return datetime.now(timezone.utc).date() The only clock the overdue rule reads. Module-level in app/storage.py and always called through the module global (never bound by `from .storage import today_utc` elsewhere), so tests can use monkeypatch.setattr("app.storage.today_utc", lambda: date(2026, 11, 30)). Todo.created_at keeps its own existing default_factory and is not affected.
- **app.storage.Todo / TodoStore** (function, modified): Todo gains a field `due_date: str | None = None` placed after created_at (stored as the validated YYYY-MM-DD string). `Todo.is_overdue(self, today: date | None = None) -> bool` (today defaults to today_utc()). `Todo.to_dict(self, today: date | None = None) -> dict[str, Any]` returns asdict(self) plus key "overdue": self.is_overdue(today); key order id, title, done, created_at, due_date, overdue. `TodoStore.create(self, title: str, due_date: date | None = None) -> Todo` (stores due_date.isoformat() or None). New `TodoStore.list_dicts(self, overdue_only: bool = False) -> list[dict[str, Any]]` reads today_utc() once and returns [t.to_dict(today) for t in sorted-by-id todos], filtered to overdue ones when overdue_only. Existing list(), get(), complete(), delete(), clear() are unchanged. The routes GET /todos and GET /todos/overdue use list_dicts.
- **tests/e2e_overdue.py** (cli, new): Usage: python tests/e2e_overdue.py <check> [base_url]. base_url defaults to $BASE_URL. Standard library only (urllib). Checks: compat (AC-1), create-future (AC-2), create-past (AC-3), boundary (AC-4), listing (AC-5), overdue-list (AC-6), empty-overdue (AC-7; with an internal --strict flag, used by local-all on a fresh server, it asserts the body is exactly []), complete (AC-8), malformed (AC-9), all (runs those nine in order against base_url), local-all (starts `python -m uvicorn app.main:app` on a free 127.0.0.1 port, polls /health until 200, runs all, always terminates the server), rollover-local (AC-10; imports app.main in-process, patches app.storage.today_utc, drives it through fastapi.testclient.TestClient). Exit 0 when the check passes, 1 with a message naming the failed assertion otherwise. No check mutates a todo it did not create. Each check creates its own todos and asserts only on those ids (plus whole-list invariants), so it passes on an instance that already holds other todos. It is not collected by pytest because the file name has no test_ prefix.

- backwards_compatibility: Additive only: existing keys keep names, types, values and order; two keys are appended; a title-only POST behaves as before; unknown request fields are still ignored.
