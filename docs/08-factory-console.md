# The Factory Console: outcomes, runs, and the first two gates in a browser

The Console is the `web` gate surface ([ADR-0007](adr/0007-pluggable-gate-surfaces.md)): a local web app over the run store and the file queue, for the people who write outcomes and decide Gates 1 and 2. It does not replace the tracker or the code host; it is the workbench for the stages before code exists, and the place where a gate is explained before it is decided.

```bash
cd orchestrator && .venv/bin/pip install -e ".[web]"
.venv/bin/factory web                 # http://127.0.0.1:8765/ opens on the run history
.venv/bin/factory runs                # the same history in the terminal; --active for the unfinished ones
```

Configuration is read from the environment and from `.env` at the repository root (`ANTHROPIC_API_KEY`, `ANTHROPIC_WORKSPACE_ID`, `FORGE_REPO`, `FORGE_TOKEN`, and the rest of [07-personal-e2e-setup.md](07-personal-e2e-setup.md)); values already set in the environment win. The Console reads `runs/<run_id>/events.jsonl` and the artifacts, and writes decisions and answers to `runs/_queue/`, exactly where `factory decide` and `factory answer` write them, so a `factory run` started from the Console or from a terminal picks them up unchanged.

## The screens

**Runs** (the home page). Every run under the runs directory, unfinished ones first, then by last activity, one row each: the line in miniature with whoever is at work standing on it, the outcome it was for, its state written as one sentence, spend against the run's budget, and when it started or how long it took ([10-console-design-system.md](10-console-design-system.md) is the contract for how every screen looks and reads). The statuses are *needs you* (a gate or a question is open), *running*, *paused at budget*, *stopped* (the controller holds no lock and recorded no failure: nothing moves the run, and a decision on its open gate is not picked up, until a controller drives it again), *done*, *closed* (rejected at a gate), *failed*, and *escalated*. The sentence says what the run produced or why it ended: "2 pull requests opened: 1 verified in dev, 1 open", "Design run: 4 specs approved, nothing built", "Closed at Gate 1: 'Not this quarter'", "Failed while building: RuntimeError: ...". On the run page the meta line says when spend leaves out sessions still open. Text filters narrow the list to the runs that need you, the ones in progress, the ones that finished, and the ones that did not. Status and line are derived from the event log by `summary.py` and cached per run on the log's size and mtime, never recorded, so an old run reads the same as a fresh one and the page's poll replays nothing that has not changed; `factory runs` prints the same table.

A finished run's page opens with a **What came out** card: the pull requests with how far each got (open, merged, verified in dev, closed without merging) and their links, the decisions you took with your comments, the reason it failed or escalated, spend and sessions, how long it took. Every run page opens with the state of the run as a sentence, then the line: seven stations on a belt, the crew figures standing at the current one while their sessions are open (asleep when the run is parked), grey human figures at the gates a person decided, an orange one where a decision is yours. Below it: the crew roster (every member, what each is doing or did, elapsed or cost), the story so far (cause then effect, grouped by station, newest first) and Your turn (questions answered inline, gates linked, the resume or budget decision). The work items with their stage and pull request (and the dev URL once verified there), the timeline from the event log with links to each agent session in the Anthropic Console, and every file produced with its fingerprint are folded under one summary at the foot of the page. Once pull requests exist, a **Pull requests and the dev deploy** card lists the items still waiting on a merge or a deploy, starts the change-request watcher (`factory watch <run_id>` as a background process, like Resume), and shows when it last checked; the watcher records the merge, follows the dev pipeline, and either marks the item verified in dev or opens a deploy-failure gate that appears in the Inbox like any other.

**Board.** What is waiting on a person, as a board: columns are the four phases of the line (Plan, Specify, Build, Ship), rows are who owns the work (product owner, engineer, ops, the crew), so whose turn it is is the row. Gates to decide and questions from agents carry one button each, and every card links to its run; a finished run stays on the board while a person still owes it a pull-request review or a deploy to watch. On a phone the board stacks by role and shows only the columns that hold cards.

**Budget.** A run paused at its budget (the next agent session would take it past `constraints.budget_usd`; nothing is running) shows a Budget card on its page: spent so far, the budget, what the next step could cost at most, and the smallest budget that lets it continue. One field and one button raise the budget and continue: the Console records the decision on the budget gate and starts `factory resume <run_id> --budget N` in the background, the way it starts runs. "Close the run" records a reject and applies it the same way. The gate also appears in the Inbox with its own review page (the same numbers and a number input), for deciding without resuming at once; the run page then offers "Continue the run". From a terminal: `factory decide <gate_id> approve --comment 'budget_usd: 80'` then `factory resume <run_id>`, or `factory resume <run_id> --budget 80` alone.

**Outcomes.** Saved outcomes and a form in the owner's vocabulary: what should be true when this is done, metrics with baseline and target, constraints, the repository, the owner. Saving validates against `schemas/outcome.schema.json`; each problem is shown beside its field in plain words (the field is marked invalid and described by the message), listed above the Save button, and focus moves to the first one. Opened from an app, the form starts from that app's repository, and a new outcome starts with the owner of the most recent one; both stay editable. From a saved outcome you start a **full run** (real agents through pull requests; needs the code host) or a **design run** (real decomposer, spec writers, and judge through Gate 2; no code; needs only the platform).

**Gate review.** The page is built to be read top to bottom:

1. *What you are deciding*: one sentence on what the agents did and what approving starts, the decomposer's or judge's summary, and at-a-glance counts (work items, metrics covered, items that need your judgement, open questions, automatic checks; at Gate 2 the verdict, criteria, issues the judge flagged, metrics covered by criteria).
2. *What to check*: a checklist specific to the gate, with the numbers filled in ("Dunning email sequence needs your judgement", "2 questions will use their defaults").
3. The content, structured: metric coverage as a table; work items in the order they would be built, each with its intent, what it moves, what it follows, and a note field; at Gate 2 one card per spec with the judge's issues first, acceptance criteria as given / when / then (folded when there are several contracts), interfaces, allowed paths, and test plan folded away, an approve checkbox named for its contract, and a note field. Gate 2 opens with *the decision in brief*: the judge's call, one line per contract on what it changes, what the set leaves out on purpose, and the open questions with their defaults.
4. *Your decision*, in a panel that stays on screen: what each option causes, a comment field, and the buttons. Every decision is two steps (the second button appears after a beat), so a stray click never decides. Notes left under an item travel with Request changes prefixed by the item id, which is how the orchestrator routes feedback. "Why this is safe to approve" explains the fingerprint binding ([ADR-0005](adr/0005-gates-bind-to-artifact-hashes.md)) and lists the files.

**Settings.** Readiness for the three things a run needs (agents and platform, code host, where decisions are read from), with the missing variable named; a live check that the agents in `claude-lock.json` exist on the platform and a list of recent sessions in the workspace with links to the Anthropic Console; the runs directory; and the logs of orchestrators started from the Console.

## Trying it without the platform

There is no simulated mode in the product. The Console's tests drive a scripted Ledgerline run through the real store, state machine, checks, and file queue (`orchestrator/tests/support/scripted_run.py`: a blocking question, Gate 1 with a second revision on request-changes, four schema-valid specs and a verdict at Gate 2, approve-subset, pull requests, completion), which is how the human loop is exercised without agents. To see the Console with runs in it, start a design run (needs only `ANTHROPIC_API_KEY`), or point `FACTORY_RUNS_DIR` at a directory that holds earlier runs: the history is read from their event logs.

## What it does not do yet

- No streaming of agent progress: the timeline is the event log, and session links go to the Anthropic Console for the trace.
- Gate 3 stays on the code host: the Console starts the watcher and shows what it recorded, it does not review or merge.
- No authentication: it binds to localhost and records decisions as `console`. Put it behind something before sharing it.
- The standalone page at `/gates/<id>/page` (the renderer in `surfaces/artifact_pages.py`) is the same content without the decision panel, for pasting into a tracker.
