# Platform and deployment: the preview environment, the observed dev deploy, and why agents never author infrastructure

The first version of this design ended at merge. Two gaps followed from that: nothing said what the platform expects of a change, so a spec could be "complete" and undeployable; and nothing required anyone to exercise the running system, so review judged code, not behaviour. This page closes both without adding a deployer agent. The platform already exists (at work: a GCP project, a Workload Identity Federation (WIF) identity and service account that GitLab CI runs as, shared CI templates, per-branch preview environments, a `dev` target; for the personal end-to-end test: a GitHub Actions workflow from `templates/github-actions-preview.yml` with a placeholder deploy step). The factory uses it and watches it; it does not build it. Which forge's CI and deployment records it reads is configuration ([ADR-0008](adr/0008-pluggable-forge-github-default.md)).

## 1. The platform contract is a skill, and here it is a placeholder

[`skills/platform-contract/SKILL.md`](../skills/platform-contract/SKILL.md) describes the personal-GitHub setup the factory runs against today, under the headings the factory expects: what the platform provides, what the application must define (including a **service manifest at a fixed path**), what agents must never touch, and how the factory uses the answers. **The platform team's existing skill replaces the file.** Until then it states only what the orchestrator itself does.

[`schemas/service_manifest.schema.json`](../schemas/service_manifest.schema.json) is the same kind of placeholder: a minimal, obviously extensible schema (service name, runtime, health endpoint, env vars with a secret flag, migrations command, resources) that the real schema replaces under the same filename. The orchestrator's `manifest_valid` check validates the manifest in the application repository against whichever schema is at that path; [`examples/ledgerline/service_manifest.json`](../examples/ledgerline/service_manifest.json) shows the shape.

Seven agents read the skill, one or two lines each: the decomposer so every work item is independently deployable to a preview; the spec writer so manifest changes are declared and reserved work is never specified; the spec judge for rubric criteria S11 and S12; the implementer, reviewer and security reviewer so none touches what the contract reserves; the merge judge as one of its inputs. The orchestrator uploads the copy here into each of their sessions as `/mnt/session/uploads/skills/platform-contract/SKILL.md` (`stages/common.platform_skill`) and seeds it into `.claude/skills/` of a repository it creates.

## 2. The preview environment is the end-to-end surface

Every factory branch `factory/<run_id>/<spec_id>` gets what every branch gets: the platform's CI deploys it to a per-branch preview environment and records the URL where the forge keeps it (a GitHub Deployment status's `environment_url`, or a GitLab environment's `external_url`). The factory adds no CI of its own; `templates/github-actions-preview.yml` is the minimal workflow shape for GitHub, with the deploy step left to the platform.

Three things change because that surface exists:

- **Specs declare end-to-end checks.** Each acceptance criterion carries `user_visible` (can a user, operator, or external system observe this through the deployed service?), and `test_plan.e2e` lists commands that run against a deployment (`target: preview`) or a locally started process (`target: local`), with `$BASE_URL` substituted. The deterministic `e2e_coverage` check fails any spec whose user-visible criterion has no e2e entry; rubric S12 has the judge check the flags are honest, and S11 that the spec is deployable through the contract.
- **Implementer and reviewer run them.** Both sessions receive `preview.json` (branch, pipeline status, URL) read by the orchestrator from the forge, never from an agent. The implementer runs the entries and records them; the reviewer runs them again and probes the deployed instance the way it probes the code. A `user_visible` criterion the reviewer could not exercise against the preview is `not_assessed`, never `met`. With `FACTORY_PREVIEW=local` there is no deployment: `preview.json` says `unreachable_from_sandbox` with no URL, the orchestrator starts the service from the manifest entrypoint on its own host for its run, and implementer and reviewers start their own instance from the same entrypoint and mark the criteria `met` or `not_met` on it (`not_assessed` only when the entrypoint will not start).
- **The orchestrator's verification is the one that counts.** After each implementer round, authoritative verification checks out the head, builds a per-run virtual environment from the repository (`runtime.setup` in the manifest, else `pyproject.toml`; a failure is the deterministic check `verification_setup`), runs the spec's test commands in it, each in its own process group, then runs every `test_plan.e2e` entry in the plan's order (`verification.verify`): `preview` entries against the preview URL, `local` entries starting what they need (in local mode both run against the orchestrator's own manifest-entrypoint instance). `run_all_for_merge` includes `e2e_coverage`, `manifest_valid`, `e2e_local` and `e2e_preview`. Not run counts as failed. Rubric I9 makes it a deterministic item the merge judge cannot override. With `FACTORY_PREVIEW=managed` all of this runs in a hosted sandbox instead ([09-app-onboarding.md](09-app-onboarding.md)). The merge judge records its own per-criterion verdict in `merge_readiness.criteria`, and the run record (`run_record.py`), which the change request links once, renders that table beside the orchestrator's e2e rows.

The evidence is the same on both sides of the practitioner and academic divide. Anthropic's long-running-agent harness found agents "declare victory too early and mark features done without verifying them end to end" ([practitioners.md §3](research/practitioners.md)). SWE-Cycle measured the gap: solve rates "drop sharply in the full cycle" once environment, implementation, and tests are all required, which is why it introduces an execution-capable grader ([academic-2026.md §5](research/academic-2026.md)). A merged change request with green unit tests is where that drop hides.

For the sandbox to reach the preview, the environment's `allowed_hosts` must include the preview domain as well as the forge host; see [environments/README.md](../environments/README.md).

## 3. Stage 5: the observed deploy to dev

After Gate 3, the change-request watcher (`factory watch <run_id>`, [`watcher.py`](../orchestrator/factory/watcher.py)) sees the merge on the forge and records `cr.merged`. The platform's pipeline on the default branch deploys to `dev` exactly as it would for a human's merge. The watcher then drives Stage 5 ([`stages/deploy_observe.py`](../orchestrator/factory/stages/deploy_observe.py)) one poll at a time:

1. moves the work item `MERGED -> DEPLOYING_DEV` and records `deploy.started` with the pipeline id, found by polling through the `Forge` protocol;
2. waits for the pipeline to reach a terminal status and records `deploy.succeeded` or `deploy.failed` with a log excerpt from the failed job;
3. on success reads the dev URL from the `dev` deployment or environment record, runs the spec's `test_plan.e2e` entries (the `preview` ones; "preview" means "a deployed instance") plus the operator's optional smoke suite (`FACTORY_SMOKE_COMMANDS`), and records `e2e.dev_passed` or `e2e.dev_failed`. A run verified in managed mode records those entries as blocked instead, because no hosted dev-test adapter exists yet, so its items reach the gate in step 5;
4. on success moves the item to `DEPLOYED_DEV`, the terminal state the Console shows as verified in dev;
5. on any failure opens a `DEPLOY_FAILURE` gate carrying the log excerpt. The human's options: `request_changes` moves the item back to `IMPLEMENTING` and stores the comments and log excerpt as `<spec_id>-deploy_feedback.md` (nothing starts that implementer round yet; see [07-personal-e2e-setup.md §10](07-personal-e2e-setup.md#10-known-gaps-before-this-is-routine)), `approve` says the failure was the platform's and the next pipeline should be watched (once), `reject` closes the item.

The pieces (`ensure_deploying`, `observe_once`, `open_deploy_failure_gate`, `apply_deploy_decision`) each read the event log before appending, so a watcher restarted at any point continues rather than repeats: an item already deploying is not moved again, an open gate is polled rather than re-opened, a recorded decision is applied. The one thing a restart repeats is an observation interrupted mid-pipeline, recorded as a second `deploy.started` with the same `attempt` number (`attempt` counts the deploy-failure gates opened since the merge).

Promotion beyond `dev` is a human act outside the factory. The outcome's `success_metrics[]` now accept `measured_at` and `measured_value` so a human can close the loop from code to business outcome later; no agent sets them.

## 4. Forge assumptions

**GitHub (default).** `forge/github.py` reads Actions workflow runs (optionally scoped to `FACTORY_DEPLOY_WORKFLOW`) and the Deployments API. The preview URL for a branch is the newest deployment for that `ref` with an `environment_url` on its latest status, else the latest deployment to the environment `<FACTORY_PREVIEW_ENVIRONMENT_PREFIX><branch>` (or its slug), which is what the template records, since it deploys the commit sha as the `ref`; the dev URL is the latest deployment to the `dev` environment. These reads are **marked unverified**: field names follow the REST documentation (2022-11-28) and are exercised only against a fake transport in tests. The first run in [07-personal-e2e-setup.md](07-personal-e2e-setup.md) verifies them.

**Self-hosted GitLab (work).** The instance is not reachable from where this design was written, so:

- Nothing here calls it. `FORGE_URL` is the only place the host is configured; the GitLab host in `environments/factory-cloud.yaml` is a commented placeholder.
- The pipeline, jobs, environments, and deployments methods in `forge/gitlab.py` follow the GitLab REST documentation (GitLab 16/17 shapes) and are **marked unverified**. Field names, the environment naming convention for previews (`preview/<branch>` by default, `FACTORY_PREVIEW_ENVIRONMENT_PREFIX` to change it), and whether the deploy job registers `environment:url` are hypotheses until the roadmap spike runs them against the real instance.
- Identity is the platform's: GitLab CI deploys with its WIF binding and service account. The factory holds no GCP credential and needs none.

## 5. Why agents do not author infrastructure

Nothing in the factory creates a service account, edits a firewall rule, changes a CI template, or touches the platform repository, and no agent deploys anything. Four reasons, each with its source:

1. **Boundary-crossing actions belong to humans or to the platform's own automation.** 12-Factor Agents models human contact as a tool call routed by a deterministic outer loop (Factor 7, [practitioners.md §1b](research/practitioners.md)); OpenAI's auto-review work routes exactly the sandbox-boundary actions to a reviewer and stops the trajectory on repeated denials ([practitioners.md §4](research/practitioners.md)). Infrastructure is the boundary. Here the platform team already made those decisions in templates, so the factory inherits them instead of re-deciding per run.
2. **Infrastructure drift is invisible to the deterministic checks.** `diff_scope` and `protected_tests` protect the application repository. A change to IAM or networking lives outside it and outside any test the spec can name; it would be approved by nobody and verified by nothing.
3. **An agent that can deploy will deploy to prove it is done.** The victory-declaration failure ([practitioners.md §3](research/practitioners.md)) gets worse when the agent controls the evidence. Reading the URL from the forge's deployment record, and having the orchestrator run the checks, keeps the oracle outside the agent (the harness-side acceptance oracle argument, [academic-2026.md §2 and §4](research/academic-2026.md)).
4. **Approvals bind to what was shown.** Gate decisions bind to artifact hashes (ADR-0005). A deploy triggered by an agent after approval would be a second action the human never saw. Observing the platform's own pipeline for the merged sha keeps the approved artifact and the deployed artifact the same thing.

The trade-off is accepted in [ADR-0006](adr/0006-observed-deployment-not-agent-driven.md): the factory cannot fix a broken deploy itself and depends on the platform's pipeline being reliable. When it is not, a human sees a `DEPLOY_FAILURE` gate with the log, which is the right person seeing the right thing.


## Visual browser verification

UI criteria (`surface: ui`, or user-visible criteria in a spec with a UI interface) require a preview e2e entry with a `visual` contract: persona, viewport, ordered steps, and environment name/data/authentication. Existing service checks continue to work. The app may run locally in a per-run checkout or in a platform preview of the exact head. Credentials and service setup belong to the host environment; the spec contains required environment variable names only. Use synthetic data or an isolated test tenant. Health HTTP 200 alone does not prove dependent services, authentication, or the UI.

In managed mode the e2e command is `factory:journey <name>`, and the factory owns the browser code ([post-mortem 2026-10-11](postmortems/2026-10-11-evergreen-frontier-models-pr.md) §1: a 71-line change shipped with a 1,860-line runner written for it). The implementer writes the change's journey, a small declarative JSON file, to `/mnt/session/outputs/journeys/<name>.json`; its format is in the platform-contract skill. The controller validates it against the entry's visual steps, uploads it with `sandbox_tools/browser_runner.py`, and binds its sha256 into the verification request and record ([ADR-0005](adr/0005-gates-bind-to-artifact-hashes.md)); the harness refuses a journey that differs. The runner (Playwright and Chromium, preinstalled in the hosted sandbox) opens `BASE_URL`, acts by role, label or text, waits for text, takes one screenshot per step, records a demo (a GIF when ffmpeg is present), measures the viewport, watches network requests, and answers `FACTORY_VISUAL_REQUEST` with `result.json` in `FACTORY_EVIDENCE_DIR`. Two things are solved once there and tested in `orchestrator/tests` (`test_browser_runner.py`, and against a real Chromium in `test_browser_runner_playwright.py`): **blocked versus failed** (blocked when the app could not be exercised: no browser, no answer, a missing credential, a 401/402/403/407 from the app during the step; failed when an expectation about the app was false), and **credential hygiene** (every declared test secret is redacted from the report, and if one appears on screen every screenshot and the recording are deleted and the check is blocked; `visual.collect` refuses media from such a check). The journey is never committed, and the `factory_proof_in_diff` check refuses repository code that reads `FACTORY_VISUAL_REQUEST` or `FACTORY_EVIDENCE_DIR`, so a UI change's pull request adds no browser-test files. Reviewers, the security reviewer and the merge judge get the journeys as uploads, which is how a journey that would pass with the behaviour broken is caught. A finding about a journey's own plumbing only carries `target: verification`: it is recorded in the run and in `runs/_backlog/verification-findings.jsonl`, and it never blocks the change or starts another round. Never substitute a deployed main URL for the branch under test.

For a change request, the integrate stage publishes up to three screenshots and one demo from factory-runner checks (the one runner that checks the screen for credentials) that passed on the approved head, at the requested viewport, with no credential ever on screen. On GitHub they go to the orphan `factory-evidence` branch (images and GIFs inline, a video as a link); on GitLab they go through the project uploads API; neither puts media in the diff ([ADR-0012](adr/0012-pr-media-without-media-in-the-diff.md); `FACTORY_PR_MEDIA=off` turns it off). Every other screenshot and recording stays in the run record.

For an attached browser worker, use command `factory:browser`. The controller publishes `runs/<run>/verify/visual/<id>/request.json`, keeps its local preview alive, and waits up to the e2e deadline (default 900 seconds). Pending requests are visible in the Console run API (`browser_checks_pending`) and page. A worker reads the request, performs the steps in the actual browser, and atomically writes `result.json` in that directory. This handoff does not launch another paid agent or change any browser permissions. A missing worker times out as blocked. A `closed` marker or expired request means do not submit more evidence. Autonomous deployments must supply a browser adapter/worker; Managed Agents' built-in browser tool is not currently available, so cloud compute alone does not satisfy this dependency.

The supported worker today is an **attached Claude Code session with Claude in Chrome connected** (`orchestrator/factory/browser_worker.py`). From that session: `factory browser list` shows open requests, `factory browser claim <id>` claims one exactly once and prints a brief with a report draft, the session drives Chrome and saves a screenshot per step (`save_to_disk`), and `factory browser submit <id> --draft <file>` publishes media and then `result.json` atomically. `submit` runs the controller's own `visual.collect` on a staging copy first, and refuses: an overall status the steps do not support, a passed step without its own screenshot or at a measured viewport other than the requested one, media older than the claim, a checkout that is not exactly the requested commit (moved HEAD, uncommitted or untracked source; ignored build output is fine), a non-loopback app, and a closed or expired request. `factory browser block <id> --reason ...` reports a check that could not run, so the controller stops waiting. `resize_window` sets the window's outer size, so the worker measures the outer-minus-inner difference and re-measures until the page viewport is exact. In a visible window this reached 1024×700. A narrow 412×915 responsive viewport was also reached, but Chrome's minimum window width kept this setup at 406 px or wider, so 390 px checks are reported `blocked`. There is no device emulation, so a narrow viewport is not a phone (no touch, no mobile user agent). Unattended workers are not available: Chrome integration needs a claude.ai login in the standalone CLI, and `factory browser doctor` reports whether one exists. GIF export goes through Chrome's downloads, so a profile set to ask where to save shows a native Save dialog that a person must confirm. See [claude-browser-worker-handoff.md](claude-browser-worker-handoff.md).

The result format is:

```json
{
  "request_id": "copy the controller request id",
  "head_sha": "copy the tested commit from the request",
  "status": "passed",
  "runner": "Claude in Chrome",
  "summary": "Observed behavior, including any coverage limitations",
  "steps": [{"status": "passed", "observation": "What was actually visible for the corresponding requested step"}],
  "media": [
    {"file": "result.png", "role": "screenshot", "caption": "The selected model is visible"},
    {"file": "enhancement.mp4", "role": "demo", "caption": "A short recording of the enhancement"}
  ],
  "demo_note": "Explain when a recording was unavailable"
}
```

Every planned step needs an observation and status (`passed`, `failed`, `blocked`). A pass needs a successful command, all steps passed, and at least one screenshot. Video is optional; preserve a short successful demo, not only failure recordings. PNG/JPEG/WebP screenshots and MP4/WebM/GIF demonstrations are supported. Use captions and step observations as the text equivalent. Do not record real personal conversations or keys. Files are bounded to 30 MiB each, 64 MiB per check, 12 files; filenames are basenames, symlinks are rejected. Media fingerprints and controller-owned request identity are stored immutably. This validates provenance and coverage, not the semantic truth of a worker's claims: an independent visual reviewer still assesses the images and experience.

The Crew run page puts **See the change** above the roster, with native video controls and no autoplay. Expand coverage/environment details for the full steps. Older-commit recordings are labeled and never satisfy a new verification. The artifact endpoint serves binary media with MIME validation and range support. The existing Console is a local, unauthenticated tool; media stays in its local run store. Do not expose this server publicly.

Local manual checks follow the repository's own tool policy (Evergreen uses Claude in Chrome for those); hosted verification uses the factory's runner. Evergreen is the first intended integration: choose its repository, refresh the curated frontier model catalog using current provider evidence, and demonstrate opening the picker, selecting an eligible new model, sending a synthetic prompt, observing streaming, and reopening the saved test conversation. Run mobile/keyboard and error/BYOK paths as separate checks. Its IAP/Convex identity and isolation must be tested in an appropriate test environment; a localhost auth shortcut cannot count as production-auth coverage.
